## How to read this matrix

- `Declared prerequisites` records prerequisite wording found in the SQL
  header. `UNVERIFIED` means no explicit prerequisite comment was found; it
  does not mean none exist.
- `Objects and effects` lists recognized table/column/function/trigger/policy
  names and categories of ACL, RLS, or DML changes. Static extraction may miss
  dynamic SQL, indirect dependencies, or statements assembled by functions.
- `Rerun / data risk` flags replacements and data-changing patterns.
  `IF NOT EXISTS` or `CREATE OR REPLACE` syntax does not establish semantic
  safety on a populated target database.
- Historical SQL rows are local source only. Prior live facts were supplied
  separately and do not prove any repository file is applied or that deployed
  function bodies match.

## Ordered rollout and dependency guidance

### Phase 0 corrective rollout

The corrective rollout is forward-only and is not a fresh-install baseline:

1. `profile-access-expand.sql`
2. `commission-transition-hardening.sql`
3. `phase0-permission-hardening.sql`
4. `commission-payment-simulation-lockdown.sql`, after
   `commission-payment-cancellation-coordination.sql` (the latest source that
   re-grants authenticated access) and the current `start_commission(uuid)`
   payment guard
5. `profile-access-hardening.sql` (contract, only after the frontend/legacy
   client gate)

The payment lockdown blocks authenticated simulated success and direct table
writes, and requires trusted provider verification before a payment-gated
commission can start. Reapply it after any later function or grant
replacement. The complete release gate and
front-end sequence are in [PHASE0-DEPLOYMENT-RECOVERY.md](./PHASE0-DEPLOYMENT-RECOVERY.md).

### Feature dependencies

The SQL headers document only partial module dependencies. For a fresh install,
start with `schema.sql`, then select required modules and follow each file's
explicit prerequisites. The source suggests `profile-repair.sql` and
`add-usernames.sql` after the core schema; `artworks.sql` after core/profile
setup; `protection.sql` after `artworks.sql`; `artwork-publication.sql` only
after the artwork, verification-preview, and deliverable prerequisites named
in the setup guide; and chat/commission corrections after their canonical
foundation functions. Dependencies not explicitly named in a SQL header are
**UNVERIFIED** until validated against the target schema.

**Do not execute the 77 files alphabetically or as a batch.** On an existing
project, reconcile live objects and migration history first, apply only
reviewed missing forward migrations, and validate every data backfill before
execution.

### Replacements and data-change warnings

- `chat-fresh-threads-after-deletion.sql` is explicitly corrected by
  `chat-canonical-per-user-reset-correction.sql`; do not rerun the older
  migration as a substitute for the correction.
- The commission-start guard files are successive revisions:
  `commission-start-payment-guard.sql`,
  `commission-start-public-post-payment-guard.sql`, then
  `commission-start-symmetric-public-post-payment-guard.sql`. Confirm which
  owner-role model is required and apply only the appropriate latest definition
  after its prerequisites.
- Multiple commission, verification, artwork, chat, and marketplace files
  replace functions with `CREATE OR REPLACE`. The matrix lists repeated
  signatures where recognized; later definitions may depend on new columns or
  policies, so do not cherry-pick by filename alone.
- Chat canonicalization and role-symmetry/artwork-publication migrations may
  merge or backfill existing rows. Review their data reconciliation and row
  counts before use.
- Files using `DROP POLICY` to replace policies are forward changes; confirm
  the whole migration completed before assuming the prior policy remains.

## Confirmed-live evidence and validation boundary

Prior user-supplied confirmed-live results identified broad profile SELECT
exposure, profile column grants, an Auth profile trigger, specific excess
RPC/Storage-helper EXECUTE grants, and private Storage buckets. They describe
the inspected live state at that time only. They do not prove any listed SQL
file was applied or that no schema drift occurred afterward.

This matrix is generated from repository SQL headers and statement names. It
does not introspect a database, validate PostgreSQL syntax, or prove RLS
behavior. Supabase CLI, Docker, and PostgreSQL client tools were unavailable;
no remote connection or production SQL was attempted. Prior PGlite checks are
isolated fixture tests, not live Supabase validation.
